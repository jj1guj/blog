## はじめに

https://rikiyat.github.io/blog/weight-space-programming/ でLLMにネットワークの重みを直接書き換えさせるのが話題になっていたので試してみた。

今回はWCSC36で使用したResNet36x512のモデルからResNet10x154への蒸留と強化を試してみた。
来年のWCSC37ではハードウェアの都合上大きなモデルを搭載できないため、知識蒸留等を行って小さいモデルで精度を上げる必要があるが、これがうまくいけばほとんど学習をさせずにモデルの精度を上げられるとの目論見がある。

## 実験条件

今回はGitHub CopilotでモデルをClaude Opus5.5をに設定して実験を行った。

ネットワークの重みはONNX形式で渡した。
ただしGitHub CopilotのClaude Opus5.5だとONNXファイルを直接読み込むことができなかったため、プロンプトでONNXファイルのパスを与えて読み込ませた。

機械学習ライブラリやcshogiなどのツール及び学習データ・棋譜の使用は学習用途以外での使用のみ認めた。

また、プロンプトで以下のリンクを渡し、この手法に則ってパラメータを編集するように指示した。


https://rikiyat.github.io/blog/weight-space-programming/

## モデルの解析

手始めにResNet35x512とResNet10x154のモデルの解析をさせ、どのブロック・チャンネルでそれぞれどのような役割を担っているか解析させてみた。
それらしい解析結果が出てきたが検証のしようがないため正しいかどうかは不明である。

### ResNet35x512

LLMの解析結果をそのまま貼る。

#### 全体の構造
- 構成は、入力層、BN（バッチ正規化）、残差ブロック35個（3×3畳み込み 512→512）、policy と value の2つのヘッドです。
- **512本のうち320本は、入力層の BN の γ が 0 です。** 生の入力を受け取るのは192本だけで、残りの320本は途中のブロックが計算結果を書き込むための空きチャンネルになっています。
- **ブロック6は重みがすべて0**（バイアスのみ）で、実質的に何もしていません。
- 書き込みの量はブロック0〜11では小さく（ノルム0.2〜0.7）、ブロック12以降で増え、**ブロック27・33・34が最大**（2.3〜2.9）です。

#### 入力層：生の入力情報を受けるチャンネル

|---|---|
| 利き数（自・敵） | 3.7〜3.9（最大） |
| 駒の配置 | 約3.0 |
| 利き | 約2.7 |
| 王手 | 1.5 |
| 持ち駒 | 約0.5（歩の5枚目以降はほぼ0） |

個別の特徴で最も重視されているのは、**自玉と敵玉の利き、利き数1以上、歩と香**です。代表的なチャンネルは次のとおりです（3×3カーネルは、ほぼ中央の1マスだけに重みがあります）。

**玉と金のチャンネル（ch470、ch237、ch86、ch418）は、多くのブロックが読みに行く中心的なチャンネル**です。後段で生まれる重要なチャンネルも、主にこの4本から作られています。

まとめると、評価は**玉の安全度（ch329、ch500）が中心**です。そこに、**大駒の成り駒（自馬は＋、敵の馬・竜は−）と自分の利きの厚み（ch166）** が加わっています。盤上のマス別に見た value の感度は、四隅と盤の端が大きくなりました。これはゼロパディングによる影響を含むので、そのまま「隅が重要」とは読まないでください。

#### policy（指し手）に効くチャンネル
- **ch309 と ch397 は、ほぼすべての移動ラベルで上位**に入ります。「何かが動ける」ことを表す汎用のチャンネルです。
- 成るかどうかで使われるチャンネルが分かれます。不成では ch397 と ch309、成りでは ch317・ch469・ch448 が中心です。
- 桂の移動では ch224・ch324・ch218 が専用に使われています。
- 駒打ちは、持ち駒を表すチャンネルと直接つながっています。
  - 打香→ch12、打桂→ch369
  - 打銀→ch368・ch117
  - 打角→ch384、打飛→ch447
  - 打金は上位が ch424・ch40 で、持ち駒の金 ch177 は12位

  なお、打歩は ch174・ch172 で、持ち駒の歩 ch297 は59位と、つながりは弱めです。
- **value の上位30本と policy の上位30本は1本も重なりません。** 最後の段階で、評価用と指し手用にチャンネルの役割がはっきり分かれています。

#### 全体の特徴
- **使われていない部品がほとんどない**：残差ストリーム、中間チャンネル、value のマップに、使われていないものはありません。value の隠れユニットも、使われていないのは1個（93）だけです。
- **重複した部品もない**：同じブロックの中間チャンネルどうしの方向の類似度は最大0.54、value の隠れユニットどうしでも最大0.76でした。
- **入力層で γ=0 の残差チャンネルが20本ある**：ただしブロック0・1が値を書き込むので、層2以降はすべて働いています。
- **ブロック9の書き込みが最大**：書き込み量は他の3〜4倍で、出力を最終的に組み立てる役割です。

| その他 | 154個のうち103個は、1個だけ無効化しても value の誤差の変化が0.001未満 |

- **線形近似の精度**：value ヘッドを ReLU を無視して線形化した評価値は、実際の評価値と相関 0.983 です（z = 3 ↔ 近似値 約7.0）。

## ネットワークパラメータの書き換え

上記の解析結果を基にネットワークパラメータの書き換えを行った。

書き換え内容は以下の通り。

* 入玉ゲートの書き換え
  * 入玉局面で駒の損得に過剰反応する`value_fc1`の24ユニットにおいて、入玉の目印（マップ24の敵陣1〜3段、マップ21の自陣7〜9段）の重みを0.02減らした
    * 入玉局面での駒の損得への過剰反応を抑える狙い
* バイアス補正
  * 悲観的な評価（−0.11）を打ち消すため、`value_fc2.bias`を +0.1 にした
* 評価値の補正
  * `value_fc2` の重みとバイアスを1.2倍にして、中程度の評価値を広げた
  * 使われていなかった隠れユニット146・42で、大差の局面における評価値の伸びを抑える折れ線を作った

この書き換えを行い、書き換え前とResNet35x512に対するvalue・loss及びテストデータに対するaccuracyの計測を行った。
テストデータにはDL将棋本付属のテストデータを使用した。(floodgate_test_2017-2018_r3500_eval5000.hcpe)

**ResNet35x512に対する計測結果**
| モデル | policy loss | value loss（logit の L1） | policy accuracy |
|---|---|---|---|
| 元のモデル（resnet10x154-144） | 1.4436 | 0.6178 | 69.37% |
| **書き換え後モデル** | **1.4436** | **0.5787** | 69.37% |

**テストデータに対する計測結果**
| モデル | policy accuracy | value accuracy |
|---|---|---|
| 元のモデル（resnet10x154-144） | **0.4883** | **0.7567** |
| 書き換え後モデル | **0.4883** | 0.7546 |
| ResNet35x512（参考） | 0.5469 | 0.7840 |

ResNet35x512に対するvalueのlossを低くし、評価値のスケールを近づけることはできたがpolicyの分布を近づけることができなかった。
また、テストデータに対するvalue accuracyは書き換え前に比べてわずかに悪化した。

## 対局実験

パラメータ書き換え前と書き換え後でどれくらい強くなったか計測するための対局実験を行った。

思考エンジンにはやねうら王(`YANEURAOU_ENGINE_DEEP_TENSOR_RT_UBUNTU`)を使用し、探索パラメータはデフォルト値を使用した。
[やねうら王互角局面集2025](https://github.com/yaneurao/YaneuraOu/releases/tag/BalancedPositions2025)を初期局面とし、1分2秒フィッシャーで200局対局した結果を以下に示す。
なお勝率において引き分けは0.5勝0.5敗として計算している。

**パラメータ書き換え前と書き換え後の対局結果**

|書き換え後モデルの勝敗|書き換え後モデルの勝率(%)|
|:--:|:--:|
|77勝91敗32分|46.5|

レート差は-24.4±44.4となり、有意差はなくネットワークパラメータ書き換えの効果はなかった。

## 対局実験の棋譜解析

対局実験の棋譜解析を行い、パラメータ書き換え後モデルの敗因を分析した。
その結果を以下に示す。

**入玉の有無ごとの勝敗・勝率内訳**
| 局の種類 | 局数 | 書き換え後モデルの勝敗 | 書き換え後モデルの勝率(%) |
|---|---|---|---|
| 入玉なし | 138 | 48勝60敗30分 | 45.7 |
| 書き換え後モデルだけ入玉 | 13 | 10勝3敗0分 | 76.9 |
| 元のモデルだけ入玉 | 16 | 9勝6敗1分 | 59.4 |
| **相入玉** | **33** | **10勝22敗1分** | **31.8** |

* **宣言勝ち**: 元のモデル 17局、書き換え後モデル 6局
* **相入玉**: うち19局は両方入玉した時点で点数負けしていた

この表から相入玉の将棋の勝率が著しく低く、正確に局面を評価できていないことがわかった。
これは入玉ゲートを書き換えた影響であると考えられる。
入玉局面の駒の損得に対する過剰反応はあくまでResNet35x512と比べたときの話であり、実際にはこれによって入玉将棋の点数勝負で有利に働いていたようだ。

## 対局実験の棋譜解析を踏まえたパラメータの書き換え

相入玉の勝率が著しく低くなったことを踏まえ、再度パラメータの書き換えを行った。
書き換え内容は以下の通り。

* これまでの書き換え内容の破棄
* ブロック7の中間ch104 の残差チャンネルへの書き込み要素をすべて0に
  * 相手の利きや自玉・相手玉の利きが少ないマスで働き、成る手を抑制しないように

2回目の書き換え後のDL将棋本付属のテストデータに対する計測結果は以下の通り。

**テストデータに対する計測結果**
| モデル | policy accuracy | value accuracy |
|---|---|---|
| 元のモデル（resnet10x154-144） | **0.4883** | 0.7567 |
| 書き換え後のモデル | **0.4883** | 0.7546 |
| 2回目の書き換え後のモデル | 0.4882 | **0.7569** |
| ResNet35x512（参考） | 0.5469 | 0.7840 |

元のモデルに対し誤差の範囲内でしか精度が向上しておらず、ネットワークパラメータ書き換えの効果が薄いと判断したため、対局実験は行わずここで打ち切った。

## まとめ

Weight-Space Programmingの記事を参考に将棋AIのモデルで知識蒸留・改善ができないかを検証した。
その結果、モデル内のどのブロックのどのチャンネルでどのような役割を担っているかを解析することはできたが、ネットワークパラメータの書き換えにより元のモデルより強くすることはできなかった。

今回参考にした記事がミスリーディングをしているという記事もあり、効果は限定的であると考えられる。

https://honnibal.dev/blog/astra-read-write-misleading

今後は実際に知識蒸留を試し、知識蒸留を行ったモデルと行っていないモデルでどのような差があるかLLMに解析させてみる予定である。
